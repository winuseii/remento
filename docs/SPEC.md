# Remento — Specification v0.2

**Supersedes v0.1. The architecture changed completely; §1, §2, §6 and §9 are rewritten.
Everything else carries over. Mark it up and send it back.**

A flashcard and spaced-repetition system for Vinu's BTech coursework. Cards are written by him or
generated by an AI from his own slides and textbooks, imported in a fixed format, and drilled on
laptop and phone against one shared schedule.

Target scale: **10,000 cards across eight semesters.**

## 1. Architecture

```
GitHub Pages  ──  static app        one HTML file + JS + manifest + service worker
                        │
                        ▼
Supabase (ap-south-1)
      ├── Auth          magic link → later Google
      ├── Postgres      cards, structure, schedule, review history
      └── Storage       card images, private bucket
```

No server to run. The page is public; the data is not.

### 1.1 Why the anon key in a public repo is safe

The key shipped in the page is the **anon key** — it is designed to be published. It grants nothing
on its own. Every table has row-level security with a single policy: `user_id = auth.uid()`. Without
a signed-in session the key can read zero rows and write zero rows. This is Supabase's intended
deployment model, not a workaround.

What *is* public is the repo: anyone who finds it reads the source. They do not get your cards.

### 1.2 Database schema

```sql
-- ── structure ──────────────────────────────────────────────────────────────
create table semesters (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users on delete cascade,
  slug        text not null,                    -- 's3', 'general'
  label       text not null,                    -- 'Semester 3'
  position    int  not null default 0,
  created_at  timestamptz default now(),
  unique (user_id, slug)
);

create table subjects (
  id            uuid primary key default gen_random_uuid(),
  user_id       uuid not null references auth.users on delete cascade,
  semester_id   uuid not null references semesters on delete cascade,
  slug          text not null,
  name          text not null,
  code          text,
  color         text,
  units_declared int,                           -- syllabus unit count; null = undeclared
  limits        jsonb not null default '{}',    -- per-subject daily caps
  position      int  not null default 0,
  unique (user_id, semester_id, slug)
);

create table units (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users on delete cascade,
  subject_id  uuid not null references subjects on delete cascade,
  no          int  not null,
  title       text not null,
  unique (subject_id, no)
);

-- ── cards ──────────────────────────────────────────────────────────────────
create table cards (
  id           uuid primary key default gen_random_uuid(),
  user_id      uuid not null references auth.users on delete cascade,
  subject_id   uuid not null references subjects on delete cascade,
  unit_id      uuid references units on delete set null,   -- null = subject-level card
  type         text not null check (type in ('qa','cloze','formula','list','numerical','image')),

  content      jsonb not null,        -- type-specific, see §2.2
  why          text,
  trap         text,
  source       text,
  figure_ref   text,
  note         text,
  importance   smallint default 2 check (importance between 1 and 3),
  marks        int,
  tags         text[] not null default '{}',
  images       jsonb  not null default '[]',

  reverse_of   uuid references cards on delete cascade,
  suspended    boolean not null default false,
  starred      boolean not null default false,

  front_norm   text,                  -- normalised front text, for duplicate detection
  content_hash text,

  -- schedule, inline: grading a card is one write
  ivl           int      not null default 0,
  ease          real     not null default 2.5,
  due           date     not null default current_date,
  reps          int      not null default 0,
  lapses        int      not null default 0,
  last_grade    smallint,
  last_reviewed timestamptz,

  created_at   timestamptz default now(),
  updated_at   timestamptz default now(),
  deleted_at   timestamptz            -- soft delete = trash
);

create index cards_due_idx     on cards (user_id, due)
  where deleted_at is null and suspended = false;
create index cards_subject_idx on cards (user_id, subject_id) where deleted_at is null;
create index cards_unit_idx    on cards (unit_id)             where deleted_at is null;
create index cards_tags_idx    on cards using gin (tags);
create index cards_dupe_idx    on cards (user_id, subject_id, front_norm);
create index cards_fts_idx     on cards using gin (search_tsv);   -- generated column

-- ── review history ─────────────────────────────────────────────────────────
create table reviews (
  id          bigserial primary key,
  user_id     uuid not null references auth.users on delete cascade,
  card_id     uuid not null references cards on delete cascade,
  reviewed_at timestamptz not null default now(),
  grade       smallint not null check (grade between 0 and 3),
  mode        text not null,          -- drill | cram | weak | quiz
  fraction    real,                   -- tick fraction on list/cloze cards
  ivl_before  int,
  ivl_after   int,
  ms          int                     -- milliseconds on the card
);

create index reviews_user_time_idx on reviews (user_id, reviewed_at desc);
create index reviews_card_idx      on reviews (card_id);
```

RLS is enabled on every table with one policy per operation: `user_id = auth.uid()`.

**Why review history is its own table now.** In the artifact version it had to be batched into daily
documents to stay fast. In Postgres, 10,000 cards × a few hundred reviews each is a few hundred
thousand rows — trivial, indexed, and queryable. This is the single biggest reason the stats in §6
get better: they become real aggregate queries instead of client-side arithmetic over a blob.

### 1.3 Images

Private Supabase Storage bucket `card-images`, path `{user_id}/{card_id}/{uuid}.webp`.
Auto-compressed client-side before upload: longest edge 1600 px, WebP, quality 0.82. A typical slide
screenshot lands around 120–180 KB.

Budget: 1 GB free storage ÷ ~150 KB ≈ **6,000 images**. Text is irrelevant by comparison —
10,000 cards of text is under 10 MB against a 500 MB database.

Paths are stored in `cards.images`; the bucket is private and served through signed URLs.

### 1.4 Trash purge

Soft delete sets `deleted_at`. On app load the client deletes rows where
`deleted_at < now() - interval '10 days'`. No scheduled job needed — the app is opened daily by
definition.

### 1.5 Offline

Not in v1. The service worker caches the app shell, so Remento *opens* without a connection, but it
cannot show cards. v2 mirrors the deck into IndexedDB and syncs the review queue on reconnect. The
PWA is built now specifically so that this stays possible.

## 2. Data model

### 2.1 Card envelope

Columns are listed in §1.2. In application terms a card is:

```
identity     id, user_id, subject_id, unit_id, type
content      content (jsonb), images
annotation   why, trap, source, figure_ref, note, importance, marks, tags
state        suspended, starred, reverse_of, deleted_at
schedule     ivl, ease, due, reps, lapses, last_grade, last_reviewed
```

Everything in `annotation` is optional. A minimum viable card is `subject_id`, `type`, `content`.

`importance` is 1–3 (★ / ★★ / ★★★), set per card, filtered at subject level.

### 2.2 The `content` shapes

**`qa`**
```json
{ "front": "State the Kelvin–Planck statement of the second law.",
  "back":  "It is impossible for any device operating on a cycle to receive heat from a single reservoir and produce a net amount of work." }
```
The `why` column gives you the Theory Drill's three-field card. There is no separate type for it.

**`cloze`** — per-blank ticking.
```json
{ "text": "Carnot efficiency depends only on {{the absolute temperatures of the two reservoirs}} and never on {{the working fluid}}.",
  "blanks": 2 }
```
All blanks hidden on the front. Reveal shows all of them, each with a tick box. The fraction is
recorded and suggests a grade (§4.3).

**`formula`**
```json
{ "prompt": "State the Clausius inequality and say what it forbids.",
  "latex":  "\\oint \\frac{\\delta Q}{T} \\le 0",
  "note":   "Equality holds only for a fully reversible cycle.",
  "symbols": [
    { "sym": "\\delta Q", "means": "differential heat transfer at the boundary", "unit": "J" },
    { "sym": "T",         "means": "absolute boundary temperature",              "unit": "K" }
  ] }
```

**`list`**
```json
{ "prompt": "Name the four processes of the Carnot cycle, in order.",
  "ordered": true,
  "items": ["Reversible isothermal expansion", "Reversible adiabatic expansion",
            "Reversible isothermal compression", "Reversible adiabatic compression"] }
```
The front shows the prompt **and the count**. Reveal shows tick boxes.

**`numerical`**
```json
{ "prompt": "Triple point of water — temperature and pressure.",
  "value": "273.16 K, 0.6117 kPa",
  "context": "The fixed point that defines the Kelvin." }
```

**`image`**
```json
{ "front": "Identify this microstructure and state its carbon content.",
  "back":  "Pearlite — alternating ferrite and cementite lamellae, 0.76 % C." }
```
with entries in the `images` column. Any card type can carry images; `image` as a *type* just means
the picture is the question.

**Reverse cards.** `reverse_of` points at the parent. Independent schedule. Off by default; the
import spec sets it only on formula cards and clean term↔definition pairs. Editing the parent updates
both; deleting the parent cascades.

## 3. Import

Unchanged from v0.1 except that the preview writes to Postgres in a single transaction.

### 3.1 JSON — canonical

```json
{
  "remento": 1,
  "target": { "semester": "s3", "subject": "Thermodynamics",
              "unit": { "no": 2, "title": "Second Law and Entropy" } },
  "defaults": { "tags": ["second-law"], "importance": 2 },
  "cards": [
    { "type": "qa",
      "front": "State the Kelvin–Planck statement of the second law.",
      "back": "It is impossible for any device operating on a cycle to receive heat from a single reservoir and produce a net amount of work.",
      "trap": "'Single reservoir' is the load-bearing phrase — two reservoirs is just a heat engine.",
      "source": "Cengel 9e p.283",
      "importance": 3,
      "tags": ["definition"] }
  ]
}
```

### 3.2 Plain text — for quick sets and hand-editing

```
@semester: 3
@subject: Thermodynamics
@unit: 2 — Second Law and Entropy
@tags: second-law
@importance: 2

Q: State the Kelvin–Planck statement of the second law.
A: It is impossible for any device operating on a cycle to receive heat from a
   single reservoir and produce a net amount of work.
trap: "Single reservoir" is the load-bearing phrase.
src: Cengel 9e p.283
imp: 3
tags: +definition
---

F: State the Clausius inequality and say what it forbids.
$$\oint \frac{\delta Q}{T} \le 0$$
sym: \delta Q | differential heat transfer at the boundary | J
sym: T | absolute boundary temperature | K
trap: T is the boundary temperature, not the system's.
rev: yes
---

L: Name the four processes of the Carnot cycle, in order.
- Reversible isothermal expansion
- Reversible adiabatic expansion
- Reversible isothermal compression
- Reversible adiabatic compression
---

C: Carnot efficiency depends only on {{the absolute temperatures of the two
   reservoirs}} and never on {{the working fluid}}.
---

N: Triple point of water — temperature and pressure.
= 273.16 K, 0.6117 kPa
why: The fixed point that defines the Kelvin.
---
```

Type markers: `Q:` · `F:` formula · `L:` list · `C:` cloze · `N:` numerical · `I:` image.
Modifiers: `A:` · `why:` · `trap:` · `src:` · `fig:` · `imp:` 1–3 · `marks:` · `tags:`
(`+x` adds to header tags, a bare list replaces them) · `rev: yes` · `sym:` (formula only).
Continuation lines are indented. `---` alone ends a card.

### 3.3 How cards get in

1. **Paste** — a textarea that sniffs JSON vs text.
2. **File** — drop a `.json` or `.txt`.
3. **Manual** — the in-app editor.
4. **Copy AI prompt** — §3.4.

### 3.4 The "Copy AI prompt" button

On Thermodynamics → Unit 2, press it and your clipboard receives:

- the destination
- the JSON schema and the text format, with examples
- the card-writing conventions (§3.5)
- **the fronts of every card already in that unit**, with an instruction not to repeat them
- a target count and type mix

Paste into any AI with your slides attached; paste the result back.

### 3.5 Card-writing conventions

Built into both the skill and the markdown spec.

1. **Reproduce the source's wording** for definitions and classifications. Where the source
   contradicts the standard textbook, use the source and note the difference in `trap`.
2. **Every list states its count.**
3. **Every formula card carries its trap** — sign convention, validity limit, the unit that catches
   people.
4. **One fact per card.**
5. **The front must be answerable without seeing the back.** No "Explain the above."
6. **Prefer the professor's phrasing** where slides and textbook differ.
7. **Source references optional** — added when available.
8. **Set `importance` honestly.** ★★★ = on the paper; ★ = recognise it if it appears.
9. **Set `reverse` only** on formula cards and clean term↔definition pairs.
10. **Never invent numbers.**

### 3.6 Import preview

```
Destination:  Semester 3 › Thermodynamics › Unit 2 — Second Law and Entropy   [change]

  38  new cards
   4  duplicates (matching front text)     → [skip] / [import anyway]
   2  updates to existing cards            → [update, keep schedule] / [skip]
   1  malformed                            → shown with its parse error

  Unit 2 does not exist yet.               → [create it] / [pick another]
```

- The JSON's `target` **suggests**; you confirm.
- Units are never created silently.
- Matching: `id` first, then `front_norm` within the same subject.
- **Updating preserves the schedule.** A typo fix on a card reviewed nine times does not reset it.
  A checkbox resets deliberately.
- Every row is expandable and editable before import.
- The whole import is one transaction — it either all lands or none of it does.

### 3.7 Export

- **Backup (JSON)** — cards, schedule, review history, structure. Re-importable.
- **Readable (Markdown)** — a subject or unit as clean text to hand back to an AI for
  "extend this, no repeats."

Images are referenced, not embedded. They live in Storage.

## 4. Study

### 4.1 Modes

| Mode | What it does | Writes schedule? |
|---|---|---|
| **Drill** | Due cards, optionally filtered to a subject | Yes |
| **Cram** | Everything in a subject/unit/tag, due or not, shuffled | **No** — logged, due dates untouched |
| **Weak** | Leeches (lapses ≥ 6) and starred cards | Yes |
| **Quiz** | Fixed count, timer, self-graded, score recorded | No |

All modes take the same filters: semester, subject, unit(s), tag(s), importance, type.

**Subject-mixed** is not a separate mode — Drill or Cram with a subject selected and no unit filter,
one tap from the subject screen ("Mix all units"). That is the exam-shaped case.

### 4.2 Session shape

25 cards by default, with "keep going" at the end. Adjustable. A visible finish line is what makes a
phone session start at all.

### 4.3 Scheduling

```
Again (0):  ease = max(1.3, ease − 0.20);  ivl = 0     → back this session; lapses++
Hard  (1):  ease = max(1.3, ease − 0.15);  ivl = ivl ? max(1, round(ivl × 1.2)) : 1
Good  (2):  ease unchanged;                ivl = ivl ? round(ivl × ease)        : 1
Easy  (3):  ease = ease + 0.15;            ivl = ivl ? round(ivl × ease × 1.3)  : 4

ivl capped at 365 days.  lapses ≥ 6 flags a leech.
```

**Suggested grade from tick boxes** (list and cloze), overridable:

```
all correct     → Good
≥ 60 % correct  → Hard
< 60 % correct  → Again
```

The fraction is stored on the review row regardless of the grade pressed, so the stats know the
difference between "I pressed Good" and "I got 4 of 5."

**Daily limits.** 20 new / 120 reviews per day, global, with per-subject overrides. Editable.

## 5. Browse, edit, search

### 5.1 Browse

| ★ | Front | Type | Unit | Tags | Due | Ivl | Reps | Lapses | Retention |
|---|---|---|---|---|---|---|---|---|---|

Sortable on every column. Sorting by lapses finds what is actually killing you. Paginated — at
10,000 cards the table loads a page at a time, never the whole deck.

Multi-select gives: move to unit, add/remove tag, set importance, suspend, star, delete, reset
schedule.

### 5.2 Edit toggle

Off: Drill shows only the card and grades; Browse is read-only.
On: an edit pencil on the drill card (fix a typo mid-review without losing your place), editable
Browse rows, bulk actions, New Card.

### 5.3 Trash

Soft-deleted rows, restorable with their schedule intact, purged 10 days after deletion.

### 5.4 Search

Postgres full-text search across front, back, formula text, symbols, tags, source, trap and note.
Results grouped by subject. `tag:derivation` and `subj:thermo` filter instead of searching.

This is one of the things the database buys you: at 10,000 cards, client-side search over a blob
would be unusable.

## 6. Stats

Now real SQL aggregates rather than client-side arithmetic.

### 6.1 Per subject

- **Cards by unit** — the coverage bar. Unit 4 having 3 cards while the rest have 40 is the most
  useful thing on this screen.
- **Maturity split** — new / learning / young / mature.
- **Retention** — of the last 30 days' reviews on this subject, the fraction graded Hard or better.
- **Worst cards** — top 10 by lapses.
- **Review heatmap** for the semester.
- **Retention by tag** — which *kinds* of thing you fail, across subjects. Only possible with a real
  database, and probably the most interesting number in the app: if your `derivation` retention is
  54 % and your `definition` retention is 91 %, that tells you how to spend a week.

### 6.2 Global

Due now, done today, streak, total cards, reviews over time.

### 6.3 The readiness number — read this before trusting it

```
Readiness(subject) = 100 × ( 0.45·Maturity + 0.35·Retention + 0.20·Freshness )

  Maturity   = fraction of the subject's cards with interval ≥ 14 days
  Retention  = fraction of the last 30 days' reviews graded Hard or better
  Freshness  = fraction of the subject's cards not currently overdue
```

**What it measures:** how well you know the cards you have made.

**What it does not measure:** whether those cards cover the syllabus. A deck holding two of five
units can report 94 %. That is the exact failure mode that gets people in exam halls.

So it is never displayed alone:

```
Thermodynamics    Readiness 94%    Coverage: 4 of 6 units · 0 cards in Units 5, 6
```

`subjects.units_declared` exists solely so this line can be honest. If you have not declared the
unit count, the app shows `Coverage: undeclared` and greys the readiness figure out. A confident
number with no denominator is worse than no number.

Keep it one semester. Kill it if it lies.

## 7. Design

*(Unchanged from v0.1.)*

I scanned the current crop of flashcard apps. They are uniformly the same thing — a white card in a
coloured box, a progress bar, a streak flame. Nothing worth copying, so this comes from your
constraints instead.

### 7.1 Direction

**Split personality, deliberately.**

- **The drill surface is calm and paper-like.** One card, serif question text, generous space,
  almost no chrome. At 1 a.m. in your fifth hour of Thermo a dense instrument panel is hostile. This
  is 95 % of your time in the app and should be the quietest thing on your phone.
- **Every other surface is an instrument.** Browse, Stats, Import: mono type, tight rows, dense
  numbers, no decoration.

One palette, one accent, tying them together.

### 7.2 Palette

```
--bg        #0A0B0D    page
--surface   #131519    card, panel
--surface2  #1A1D22    raised, hover
--line      #24282E    hairline
--line2     #363C45    emphasis border

--tx        #E9E7E3    primary text
--tx2       #A0A39A    secondary
--tx3       #6B6F76    tertiary, labels

--sc        #EF3B42    scarlet — brand, primary action, active tab
--sc-hi     #FF5C62    hover
--sc-dim    #7A1F24    de-emphasised
--sc-bg     #2A1013    tint
```

**Grade buttons are not coloured fills.** Scarlet is the brand, so a scarlet "Again" would fight it.
The four grades are neutral outlines with a coloured left edge and coloured label:

```
Again  #F2555A      Hard  #D9822B      Good  #3FB27F      Easy  #4B8BD4
```

The only filled scarlet element on the drill screen is **Show answer** — one saturated thing, and it
is always the thing you are about to press.

Subjects get a quiet accent in Browse and Stats, never on the drill card.

### 7.3 Type

- **Question text:** a serif (Newsreader or Source Serif 4).
- **Chrome, labels, numbers:** a mono (IBM Plex Mono or JetBrains Mono), uppercase, letterspaced.
- **Answer body:** system sans, 15–16 px, generous leading.
- **Formulas:** KaTeX at 1.1× surrounding text. Loaded normally from a CDN — no sandbox restrictions
  here, which is one of the smaller wins of leaving the artifact.

### 7.4 Layout

```
DRILL   BROWSE   IMPORT   STATS   ⚙
```

Phone: same tabs, bottom-anchored. Grade buttons in the lower third where your thumb already is.
Keyboard shortcuts on laptop — space to reveal, 1–4 to grade — and every one is also a clickable
button.

## 10. Honest limitations

- **Coverage is undecidable by the app.** Remento cannot know your syllabus. Every completeness
  number is relative to what you entered, and the UI says so rather than quietly flattering you.
- **Self-grading is a self-report,** not a measurement. You said that is the point. It also means
  retention is not comparable to anyone else's.
- **No offline in v1.** No internet, no cards. The PWA shell opens; it has nothing to show. This is
  the single largest risk the architecture carries, and v2 exists to remove it.
- **Supabase free projects pause after 7 days of inactivity.** Daily use prevents it; a long holiday
  does not. Un-pausing is one click and loses nothing.
- **Images are not in the backup.** Text and schedule survive an export; images live in Storage.
- **The repo is public.** The data is not, but the code is. Nothing sensitive goes in the repo.
- **Cram does not advance spacing,** by design. A week of cramming leaves your due queue where it
  was, which will feel wrong and is correct.
- **The scheduler is tuned by feel.** SM-2's constants are forty years old and were fitted to
  vocabulary, not thermodynamics derivations. If intervals feel wrong after a month, §4.3 is what
  changes.
- **This document still has not met a real card.** Step 3 exists because that is a genuine risk.
